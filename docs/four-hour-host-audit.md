# بررسی کندل 4H و اتصال هاست — ۲۰۲۶/۱۱/۱۰

## علت اختلاف و اصلاح

دو مسیر قبلی از timestamp صحیح UTC استفاده می‌کردند، اما OHLC همهٔ کندل‌های پایه را بدون توجه به حجم وارد تجمیع می‌کردند. در پاسخ یک‌دقیقه‌ای والکس، دقیقهٔ بدون معامله می‌تواند قیمت حمل‌شده از معاملهٔ قبل داشته باشد؛ پس این قیمت، قیمت معامله‌شدهٔ بازهٔ جدید نیست. در نمونهٔ اولیه ۱۸۹ دقیقه از ۲۴۰ دقیقه صفرحجم بود؛ Open/Low قبلی `74417.46` و Open/Low حاصل از معاملات `74479.50` است.

روش مشترک `CandleAggregation`:

- ابتدا حضور تمام timestampهای پایه، هم‌ترازی UTC، عدد متناهی و معتبر بودن OHLCV کنترل می‌شود؛ صفرحجم با دادهٔ مفقود یکی نیست.
- Open اولین و Close آخرین کندل دارای حجم مثبت است؛ High/Low نیز فقط از همین کندل‌ها گرفته می‌شوند.
- Volume مجموع حجم تمام کندل‌های بازه است.
- بازهٔ کاملاً بدون معامله کندل معتبر تولید نمی‌کند؛ علت `UNAVAILABLE: no trades in complete interval` ثبت می‌شود.
- خروجی موتور اصلی همچنان همان شکل قبلی دارد؛ ماژول اندیکاتور metadata شروع و duration را به همان نتیجه اضافه می‌کند. کلیدهای کش تاریخچه و نتیجه تغییر نسخه دادند تا مقدارهای قبلی با تعریف جدید مخلوط نشوند؛ دیتابیس پاک یا بازنویسی دستی نمی‌شود.

کد مشترک ابتدا جداگانه تست شد؛ پس از پاس شدن مقایسه‌ها به دو مسیر متصل شد. این اصلاح عمداً OHLC بازه‌های شامل دقیقه‌های بدون معامله را اصلاح می‌کند؛ schema استراتژی، شروط و تنظیمات فعال تغییر نکرده‌اند. بازهٔ تماماً بدون معامله از این پس می‌تواند ارزیابی را مسدود کند، حتی اگر API قیمت حمل‌شده ارائه دهد.

## مقایسهٔ واقعی

منبع: `GET https://api.wallex.ir/v1/udf/history` با resolutionهای `1` و `60`. فایل اولیه و ۹ دریافت تازه در fixture نگه داشته شده‌اند؛ نمونهٔ اولیه و یکی از دریافت‌های تازه یک نماد/بازهٔ مشترک دارند. بنابراین ۱۰ مقایسه، شامل ۹ ترکیب یکتای نماد/بازه است.

| شروع UTC بازهٔ چهارساعته | BTCUSDT دقیقهٔ صفرحجم | ETHUSDT | SOLUSDT |
| --- | ---: | ---: | ---: |
| 2026-11-09 20:00 | 212 | 218 | 219 |
| 2026-11-10 00:00 | 231 | 226 | 219 |
| 2026-11-10 04:00 | 189 | 219 | 213 |

در همهٔ مقایسه‌ها timestamp شروع/پایان و هر چهار مقدار OHLC یکسان بود. مجموع حجم در مرجع مستقل Python Decimal **دقیقاً** برابر بود؛ در PHP double بیشترین اختلاف حجم `1.4210854715202004e-14` بود که از ترتیب جمع اعداد ممیز شناور ناشی می‌شود، نه اختلاف معاملات. تلورانس آزمون PHP برای همهٔ فیلدها `1e-9` است. تمام مقادیر و اختلاف‌های هر بازه در [خروجی مقایسه](four-hour-comparison-results.json) هستند.

تست‌های مصنوعی، حجم صفر در ابتدا/انتها/وسط، سه ساعت پیاپی بدون معامله، نبود حتی یک دقیقهٔ صفرحجم، و صفر بودن کل ۲۴۰ دقیقه را پوشش می‌دهند. در تست یکپارچه، موتور اندیکاتور و موتور استراتژی در بازهٔ بدون معامله هیچ هشداری صادر نکردند و علت UNAVAILABLE ثبت شد.

## عیب‌یابی Failed to fetch

در Console واقعی Chrome این رخداد دیده شد:

```text
https://wallex.free.nf/public/api.php
Failed to load resource: net::ERR_SSL_PROTOCOL_ERROR
```

این شکست مربوط به **مرورگر → هاست PHP** و قبل از دریافت HTTP response است؛ در نتیجه HTTP status برای همان شکست در دسترس نیست. خطای JSON یا خطای درخواست PHP به والکس نمی‌تواند علت همین رخداد TLS باشد. از این شاهد به‌تنهایی نمی‌توان مشخص کرد ایراد در شبکه، واسط اتصال، یا لایهٔ TLS ورودی میزبان است؛ نسبت دادن قطعی آن به گواهی یا صرافی مستند نیست. برخی درخواست‌های همان مرورگر موفق بودند؛ این خرابی در آزمایش متناوب بود.

ابزار خصوصی مرورگر→PHP نیز یک پاسخ HTTP 200 با header `X-Diagnostics-PHP: reached` در حدود `196.9 ms` گرفت. TLS مستقیم این محیط به دامنهٔ هاست در چند تلاش خطای `WRONG_VERSION_NUMBER` یا قطع اتصال داد؛ اعتبارسنجی گواهی هیچ‌جا غیرفعال نشد.

## اتصال واقعی PHP هاست به والکس

این سه درخواست **از PHP خود هاست** در timestamp `1794309447` اجرا شدند، نه از کامپیوتر محلی:

| درخواست | HTTP | زمان پاسخ | JSON/schema | cURL errno | TLS |
| --- | ---: | ---: | --- | ---: | --- |
| `/v1/markets` | 200 | 502.48 ms | معتبر؛ قیمت BTCUSDT: 74185 | 0 | تأییدشده |
| history resolution=1 | 200 | 1350.19 ms | ۶۰ کندل دریافت‌شده و بسته‌شده | 0 | تأییدشده |
| history resolution=60 | 200 | 281.68 ms | ۵ دریافت‌شده؛ ۴ بسته‌شده | 0 | تأییدشده |

آخرین زمان بسته‌شدن دادهٔ یک‌دقیقه‌ای `1794309420` و دادهٔ ساعتی `1794308400` بود. این فقط مشاهدهٔ همین اجرای واقعی است؛ پایداری همیشگی اتصال را تضمین نمی‌کند.

## ابزار مدیریتی و حریم اطلاعات

`public/admin-diagnostics.php` به‌طور پیش‌فرض بدون فایل تنظیمات خصوصی، HTTP 404 می‌دهد. تنظیمات در `config/diagnostics-admin.php` خارج از مسیر عمومی و پشت `.htaccess` قرار می‌گیرند. فقط hash رمز نگه داشته می‌شود؛ کل فایل تنظیمات و گزارش خصوصی در Git نادیده گرفته می‌شوند. دسترسی نیازمند HTTPS، رمز مدیر موقت، session پانزده‌دقیقه‌ای، انقضای سراسری و CSRF معتبر برای تست upstream است. درخواست upstream در هر session محدود می‌شود. فرم رمز از نوع password است؛ رمز، cookie، CSRF و بدنهٔ کامل پاسخ در گزارش منتشر نمی‌شوند.

ابزار فقط سه URL ثابت عمومی دارد و URL دلخواه نمی‌پذیرد. `App.php`، `db()` یا scheduler را بارگذاری نمی‌کند؛ به استراتژی، هشدار و SQLite دسترسی ندارد. برای آزمایش فعلی یک تنظیمات موقت یک‌ساعته نصب شد و پس از انقضا صفحه مجدداً 404 می‌دهد. فایل `data/diagnostics-access.json` محلی و ignored، اطلاعات موقت این نشست را دارد و نباید منتشر شود.

## اجرا و محدودیت باقی‌مانده

```text
php tests/all.php
php tests/candle-aggregation.php --report
python tests/candle-reference.py
python tests/admin-diagnostics.py
node tests/details.js
node tests/notifications.js
node tests/trade.js
python tests/deployment.py
python tests/indicator-reference.py
```

پس از یکپارچه‌سازی، ۴۲۳ assertion در ۱۵ مجموعهٔ PHP، چهار تست HTTP دسترسی مدیر، چهار تست استقرار، سه مجموعهٔ رابط و مقایسه‌های مستقل Decimal پاس شدند. تست HTTP مدیر در یک سایت PHP موقت بدون پوشهٔ data اجرا شد: حالت خاموش/منقضی، دسترسی ناشناس، رمز اشتباه، ورود صحیح، ping و رد CSRF نادرست بررسی شدند.

مشکل اتصال مرورگر به هاست در لایهٔ TLS هنوز رفع زیرساختی نشده است؛ اصلاح تجمیع کندل ارتباطی با آن ندارد. هیچ سفارش واقعی، تغییر تنظیمات استراتژی، پاک‌کردن هشدار یا دستکاری دستی SQLite در این بررسی انجام نشد.
